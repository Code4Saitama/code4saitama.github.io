# Facebookグループの取得・レビュー・アーカイブ統合手順

## この文書の目的

Facebookグループの投稿、コメント、写真、Facebookイベントを、ログイン済みブラウザから取得し、公開可能な活動アーカイブへ整理するまでの手順と注意点をまとめます。

今回対象にしたのは、Code for SAITAMAの公開Facebookグループです。

- グループURL: `https://www.facebook.com/groups/186097664924714/`
- グループID: `186097664924714`
- 取得時点: 2026年8月
- 一覧で確認した投稿: 941件
- 公開用に保持した投稿: 388件
- 保持したコメント: 454件
- 保持したFacebookイベント: 123件

件数は取得時点のスナップショットです。Facebook側で投稿の削除、公開範囲の変更、コメントの追加などが行われれば変わります。

## 前提と遵守事項

取得前に、対象コンテンツを閲覧・保存・公開する権限があることを確認します。非公開グループ、参加者限定の投稿、第三者の個人情報を、権限や目的の確認なしに取得・公開してはいけません。

- ログインは利用者がブラウザ上で行い、Cookie、アクセストークン、パスワードをファイルへ保存しない。
- Facebookの利用条件、対象グループのルール、著作権、肖像権、個人情報保護を確認する。
- 機械的な大量アクセスを避け、少数のバッチに分けて進める。
- 投稿者名、プロフィールURL、メールアドレス、電話番号、オンライン会議の認証情報などは公開データから除く。
- 活動の説明に不可欠な主催者・登壇者等の氏名を残す場合も、役割と公開根拠を個別に確認する。
- 元投稿が公開されていても、アーカイブでの再公開が常に妥当とは限らない。本文と写真を別々にレビューする。

## データを3段階に分ける

この作業では、データを次の3段階に分離します。

| 段階 | 主な保存先 | 内容 | Gitへの追加 |
| --- | --- | --- | --- |
| 取得中の生データ | `/tmp/fb_*.json` | 氏名、元URL、期限付き画像URLを含む | 追加しない |
| 編集用アーカイブ | `fb_group_archive/` | 匿名化した投稿、コメント、イベント、画像 | レビュー後のみ追加 |
| 公開サイト用データ | `src/content/`、`public/` | 統合・要約済みの記録 | 追加する |

一時チェックポイントは機微情報を含みます。リポジトリ内へ置かず、共有・バックアップ時もアクセス範囲を限定します。作業終了後は、再取得の必要性と保管根拠を確認して削除します。

## 全体の流れ

1. ログイン済みブラウザでグループの投稿一覧を古い順にたどり、投稿IDと基本情報を保存する。
2. 各投稿を個別に開き、折りたたまれた本文、コメント、返信、コメント写真、イベントリンクを取得する。
3. Facebookイベントを個別に開き、日時、場所、説明、写真を取得する。
4. 期限付きURLが有効なうちに画像を保存し、マニフェストと照合する。
5. 本文を取得できなかった投稿を再試行し、取得不能なものを記録する。
6. 非関連投稿を目視レビューし、シビックテックのイベントに関連する記録だけを保持する。
7. 個人情報を削除し、本文・コメントを要約して、活動記録または関連資料へ分類する。
8. 既存のFB Page、Deep Research由来の記録と統合し、ビルドと画面を確認する。

## 1. 作業ブランチと退避を用意する

取得・選別・匿名化は分けてコミットします。特に、画像削除を伴うフィルターを実行する前に、直前の状態をコミットしておきます。

```sh
git switch -c codex/facebook-group-archive-update
git status --short
```

既存の作業ブランチを使う場合は、新しいブランチを作る必要はありません。未コミットの変更があるときは、今回の取得結果と混ぜないようにします。

## 2. 投稿一覧を古い順に取得する

Facebookのグループ画面をログイン済みブラウザで開きます。利用できる場合は投稿の並び順を「古い順」にし、利用できない場合は過去の投稿が尽きるまで読み進め、取得後に日付順へ整列します。

一覧取得時は、少なくとも次の値を保存します。

- 投稿ID
- 表示日付
- 投稿者名（匿名化前の照合にだけ使用）
- 投稿の固定URL
- 一覧上で確認できる本文
- 投稿画像のURL、代替テキスト、表示サイズ

今回の初期チェックポイントは `/tmp/fb_crawl_checkpoint.json` に保存し、`rows` 配列へ記録しました。現在の `scripts/build_fb_group_archive.mjs` はこのパスを入力として使用します。

```sh
node scripts/build_fb_group_archive.mjs
```

この処理により、日付順の `fb_group_archive/posts.json` と、投稿画像の保存先を定義する `fb_group_archive/images_manifest.json` が生成されます。ただし、この段階のファイルには個人情報と元URLが残るため、匿名化前に公開・コミットしません。

### 一覧取得の完了条件

- 最古と最新の投稿年月が想定範囲と一致する。
- 投稿IDが重複していない。
- 日付を解釈できない投稿を別途確認している。
- スクロール途中で同じ期間を循環していない。
- 件数と最終スクロール位置を作業記録へ残している。

## 3. 投稿本文・コメント・返信を再取得する

一覧画面だけでは、長い本文、遅延読み込みされたコメント、返信、コメント写真を取得できません。`scripts/fb_group_full_crawler.mjs` は、投稿ごとの再取得処理を実装したブラウザ制御用モジュールです。

このモジュールは通常のNode.js CLIでは完結しません。ログイン済みタブと、タブに対するPlaywright／画面スクロール操作を提供するブラウザ制御環境から使用します。

チェックポイントは次の形で初期化します。

```json
{
  "posts": [],
  "errors": []
}
```

ブラウザ制御環境では、概念的には次のように使用します。

```js
import { createFacebookGroupCrawler } from "./scripts/fb_group_full_crawler.mjs";

const crawler = createFacebookGroupCrawler({
  tabs: loggedInFacebookTabs,
  posts,
  checkpointPath: "/tmp/fb_group_full_checkpoint.json",
});

await crawler.batch(60);
```

`tabs` と `posts` はブラウザ制御側から渡します。実装は各投稿について次を行います。

- 投稿URLへ移動する。
- 「もっと見る」を開く。
- 表示件数に近づくまでコメントをスクロールして読み込む。
- 「返信を表示」「返信を見る」を開く。
- 投稿本文とコメント本文を分離する。
- コメントID、親コメントID、日時、固定リンクを記録する。
- 投稿画像とコメント画像を分離する。
- 投稿内のFacebookイベントリンクを収集する。
- 1投稿ごとにチェックポイントを書き戻す。
- 失敗した投稿は最大3回まで再試行対象にする。

一度に全件を処理せず、30〜60件程度のバッチで `stats()` とエラー内容を確認します。複数タブを使う場合も、アクセス負荷と画面状態の安定性を優先します。

## 4. Facebookイベントを取得する

投稿から見つかった `/events/<ID>/` リンクと、グループのイベント一覧で確認できたイベントを収集します。各イベントを個別に開き、次の値を `/tmp/fb_group_events_checkpoint.json` の `events` 配列へ保存します。

```json
{
  "events": [
    {
      "status": "recovered",
      "url": "https://www.facebook.com/events/123456789/",
      "title": "イベント名",
      "header_text": "日時・イベント名・場所を含む表示テキスト",
      "detail_text": "詳細欄の表示テキスト",
      "images": [],
      "fetched_at": "2026-08-12T00:00:00.000Z"
    }
  ]
}
```

イベント取得は今回、ログイン済みブラウザ上で実施しました。イベント専用クローラーはまだ独立したCLIとしてパッケージ化されていません。再実施時は、投稿クローラーと同じく、途中保存、再試行、重複排除を必須にします。

削除済み・非公開・閲覧制限のあるイベントは本文を推測で補完しません。IDと参照元投稿だけが確認できる場合は、未取得であることが分かる状態で残し、公開採用は別途判断します。

## 5. 取得結果を統合する

投稿とイベントのチェックポイントを編集用アーカイブへ統合します。最初は必ず `--dry-run` で件数とエラーを確認します。

```sh
node scripts/integrate_fb_group_full_archive.mjs \
  /tmp/fb_group_full_checkpoint.json \
  /tmp/fb_group_events_checkpoint.json \
  --dry-run
```

問題がなければ、`--dry-run` を外して実行します。

```sh
node scripts/integrate_fb_group_full_archive.mjs \
  /tmp/fb_group_full_checkpoint.json \
  /tmp/fb_group_events_checkpoint.json
```

主な出力は次のとおりです。

- `posts.json`: 本文、要約、コメント、イベントリンク
- `comment_images_manifest.json`: コメント画像の取得元と保存先
- `group_events.json`: Facebookイベント情報
- `event_images_manifest.json`: イベント画像の取得元と保存先
- `full_crawl_report.json`: 取得件数、欠損、エラー

`full_crawl_report.json` の `missing_posts` と `errors` が空であることだけでなく、本文あり件数、コメントあり件数、画像件数が不自然に減っていないことも確認します。

## 6. 画像を保存する

投稿・コメント・イベント画像は、各 `*_images_manifest.json` の `source_url` から `saved_path` へ保存します。Facebook CDNのURLは期限切れになるため、本文取得後に先延ばしせず保存します。

現在、汎用の画像ダウンロードCLIはリポジトリに含まれていません。今回の取得ではマニフェストをもとにダウンロードし、次を確認しました。今後自動化する場合も、同じ検証を入れます。

- 保存先が必ず `fb_group_archive/images/` の内側である。
- HTTPエラーのレスポンスを画像として保存していない。
- Content-Typeと拡張子が大きく食い違っていない。
- 0 byteファイルがない。
- 同じ写真IDまたはURLパスを重複保存していない。
- マニフェストにある全保存先が存在する。

画像の元URLは匿名化処理で削除されます。ダウンロード完了を確認してから匿名化へ進みます。

## 7. 非関連投稿を目視レビューする

自動判定だけで投稿や写真を削除しません。候補リストを生成し、本文、写真、元投稿、既存イベントとの関係を目視確認します。

```sh
node scripts/build_non_civictech_review.mjs
```

生成される `fb_group_archive/non_civictech_review.html` をブラウザで開きます。削除対象だけにチェックを入れ、`facebook-posts-selected-for-deletion.json` を書き出します。

チェック対象の例:

- 商品・サービスの宣伝だけで、地域課題や市民参加との接点がない。
- 個人の近況や一般ニュースの共有だけで、シビックテックとの関係がない。
- 本文、コメント、写真、イベントリンクのいずれにもイベント関連性がない。
- 本文を再取得できず、写真や周辺情報からも関連性を確認できない。

残す対象の例:

- Code for SAITAMAが主催・共催・参加・支援したイベント。
- シビックテック、オープンデータ、マッピング、防災、地域課題解決等のイベント。
- 告知、準備、当日記録、成果、振り返りとして既存イベントに結び付く投稿。
- 他地域の事例でも、活動上の参照・交流・協力として必要な記録。

レビューJSONは匿名化前の情報を含むため、フィルターへ渡した後は公開リポジトリに残しません。

## 8. イベント関連投稿だけに絞る

レビュー結果を `fb_group_archive/facebook-posts-selected-for-deletion.json` に置き、まずドライランします。

```sh
node scripts/filter_event_related_group_posts.mjs
```

判定結果は `/tmp/fb_event_filter_report.json` に出力されます。既存イベントとの一致、イベント表現とシビックテック表現、同日イベントなどの根拠を確認します。

問題がなければ適用します。

```sh
node scripts/filter_event_related_group_posts.mjs --apply
```

`--apply` は対象投稿を `posts.json` から除き、対応する投稿画像・コメント画像を削除します。実行前のコミットまたはバックアップが必須です。パス検証により `fb_group_archive/images/` 外は削除しない実装ですが、件数と差分は必ず目視します。

## 9. 匿名化・要約・分類する

公開用の編集処理を実行します。

```sh
npm run curate:group
```

このコマンドは `fb_group_archive/` のJSONとマニフェストを上書きします。実行前に、取得・フィルター済みの状態をコミットまたはリポジトリ外へ退避します。

この処理は次を行います。

- 投稿者・コメント投稿者を「グループ参加者」へ置換する。
- プロフィールURL、投稿URL、画像の期限付き元URLを削除する。
- 氏名候補、メールアドレス、電話番号、会議ID、パスコード等を本文から除く。
- Facebook UI由来のノイズを除去する。
- 本文とコメントの要約を生成する。
- テーマを付与する。
- Code for SAITAMAまたは埼玉の直接的な活動を `activity` に分類する。
- 外部事例や周辺情報を `reference` に分類する。
- `public_records.json` を生成する。

自動匿名化は完全ではありません。処理後に氏名、連絡先、住所、顔写真、子どもの写真、医療・福祉等のセンシティブ情報を再確認します。引用や登壇者名を残すときも、自動処理結果をそのまま採用せず編集判断を行います。

元投稿URLを直接保持しなくても、投稿IDから次の形式で公開投稿を参照できます。

```text
https://www.facebook.com/groups/186097664924714/posts/<POST_ID>/
```

## 10. インデックスとサイトコンテンツを再生成する

匿名化後の集計を更新します。

```sh
node scripts/build_fb_group_indexes.mjs
npm run export:content
npm run build
```

`npm run export:content` は `src/content/events/`、`src/content/notes/`、`src/content/slides/` を再生成します。手編集を含むため、実行前後の差分を必ず確認します。

公開画面では情報源を次の表記に統一します。

- `FB Group`
- `FB Page`
- `Deep Research`

同じイベントが複数情報源に存在するときは、重複ページを作らず、既存イベントへ投稿ID、イベントID、画像、要約を統合します。直接的な活動は時系列・テーマ別へ、外部事例や周辺情報は関連資料へ表示します。

## 11. 公開前チェック

### データ

- `full_crawl_report.json` の取得件数、エラー、画像件数を前回と比較する。
- `event_filter_manifest.json` の保持・削除件数を確認する。
- `posts.json` と `group_events.json` に個人名・連絡先・元画像URLが残っていない。
- 各画像マニフェストの `saved_path` が実在する。
- `public_records.json` の日付不明・空要約・不自然なタイトルを確認する。
- 既存イベントとFB Groupイベントが重複していない。

### 表示

- トップのカルーセルで活動写真とリンクが正しい。
- 時系列とテーマ別の一覧性が保たれている。
- 一覧から個別ページへ移動し、要約全文、コメント、画像を確認できる。
- 元投稿・元イベントのリンク形式が正しい。
- 写真なしの項目が崩れていない。
- モバイル幅でも長文・画像・タグがはみ出さない。

### コマンド

```sh
git diff --check
npm run build
git status --short
```

## 再取得・差分更新の考え方

毎回全件を取得し直す必要はありません。投稿IDとイベントIDを安定キーとして、前回チェックポイントにない項目だけを追加します。

1. 前回の最終取得日時と最新投稿IDを記録する。
2. 新規投稿の一覧だけを追加する。
3. 新規投稿と、前回エラーになった投稿だけを個別取得する。
4. コメント数が増えた投稿は再取得する。
5. 新しいイベントリンクだけをイベント取得キューへ加える。
6. 統合前後の件数差をレポートする。
7. 匿名化済みデータへ生データを直接追記せず、生チェックポイントから再生成する。

## よくある問題

| 症状 | 主な原因 | 対処 |
| --- | --- | --- |
| 投稿コンテナが見つからない | 未ログイン、ログイン期限切れ、FacebookのDOM変更、投稿の閲覧制限 | 画面を目視し、再ログイン後にセレクタを見直す |
| 「もっと見る」が開かない | ラベルや言語設定の変更 | 実際のアクセシブル名を確認し、完全一致条件を更新する |
| コメント件数が少ない | 遅延読み込み、返信の未展開、非表示・削除済みコメント | スクロールと返信展開を再試行し、期待件数との差を記録する |
| 本文が利用不可になる | 元投稿の削除、共有範囲変更、共有元コンテンツの消失 | 推測で補わず、コメント・画像・イベントとの関係も確認して採否を決める |
| 画像が保存できない | Facebook CDN URLの期限切れ | ログイン済み画面からURLを再取得し、すぐ保存する |
| 同じ画像が複数保存される | CDN URLのパラメータ差 | 写真ID、リンク先、URLパスを安定キーに重複排除する |
| イベントの日付・場所がずれる | ロケール別表記、本文中の日付との混同 | ヘッダー領域を優先し、曖昧な場合は手動確認する |
| 匿名化で団体名まで消える | 人名候補の過検出 | 団体名パターンと置換候補を見直し、差分を目視する |

## 現在の自動化の限界

- FacebookのDOMと日本語ラベルに依存するため、UI変更時はセレクタ調整が必要です。
- ログイン済みブラウザ制御が必要で、ヘッドレスCLIだけでは再現できません。
- イベント取得と画像ダウンロードは、まだ単独の再利用可能なCLIになっていません。
- Facebook上の表示コメント数と取得可能コメント数は一致しない場合があります。
- 自動分類と匿名化には誤判定があり、公開前の人手レビューを省略できません。

今後同様の案件へ適用する場合は、グループID、対象期間、保持基準、匿名化基準、公開先を設定ファイルへ分離し、イベント取得と画像検証をCLI化するのが次の改善点です。
